# osstrich — plan-to-PR for an external repo

Contribute back to a project you depend on — genuinely useful to its maintainer, and useful to you. The KPI is dual, and neither half is optional: **a pull request the maintainer would have written the same way if they'd found the bug themselves**, AND (when the fix already exists as one of your own vendored fork patches) **movement toward deleting that fork patch** — every upstream contribution either retires something you're privately maintaining or reduces a class of pain you'd otherwise keep paying for alone.

This skill covers both halves: deciding what to contribute (`discover`) and contributing it (`build`). Your own repo is context for both — `discover` reads it to find candidates; `build` reads it to know whether a target retires one of your fork patches, which of your conditions reproduce the bug, and which of your own tests must stay green. `references/repos/*.md` is this skill's own knowledge base — one file per repo you've contributed to before, callable by name the moment you touch that repo again (this directory is not included in the public skill; create it locally as you go). Nothing here restates your own project's conventions for how you work generally; those still govern how you work regardless of which repo the diff lands in.

## Stages — two entry modes

| Invocation | Runs | Loads | Use when |
|---|---|---|---|
| `osstrich discover` | D1 inventory → D2 rank → D3 overlap → D4 verdict → gate; then, after a go, `build` on each funded target | `references/discover.md` + `references/classification.md`, then the build references | "What should we contribute?" — no target named yet, or a periodic sweep |
| `osstrich build <repo \| issue \| patch>` | gate → P0–P6 (investigate, build, PR with its etiquette checkpoints, capture) | `references/investigate.md`, `references/build-and-test.md`, `references/pr-etiquette.md`, `references/self-learning.md` | A target is already named |
| `osstrich` (bare) | same as `discover` | | A fresh "let's give back" with nothing named |
| `osstrich investigate` | Phases 0–2 only | `references/investigate.md` | Just scope the problem and the repo's norms |
| `osstrich capture` | Phase 6 only | `references/self-learning.md` | Fold a just-finished contribution's learnings back in |

Invoked at a stage, assume earlier stages' outputs already exist (a verdict row for `build`; a scoped repro + root cause for Phase 3 onward; an opened PR for `capture`). `discover` writes nothing anywhere except its own run directory — its output is the verdict table, the one rulable thing.

## Operating rules

- **No code before the green-light.** Investigate and present a short plan (target repo, symptom, suspected root cause, competing approaches if any); wait for the maintainer's go before writing a diff or opening anything public. Terse directives ("execute," "open it," "go") carry full intent once the plan's been seen — don't re-ask at each sub-step after that.
- **The gate runs before any build, in both modes.** For every target: is there a different way of using the library, one that does not break your system, that makes the upstream fix optional? Verified against the library's source, never an identifier's name. Yes → the deliverable is your own migration and the upstream item becomes give-back-only. No → upstream is the fix. See `references/discover.md` → The gate.
- **Fund only on overlap; community before company.** A candidate is funded when one of your next steps — explicit on your backlog, if you have one, or inferred from your own workarounds, pins, and hand patches — depends on an upstream item, AND you hold evidence upstream lacks. Give-back-only items are offered as candidates only when nothing overlaps. Company-produced projects and tools about a company's product rank behind every community project; they are deferred, never removed. See `references/discover.md` → D2, D4.
- **Every run writes its partials to a run directory and ends with one run record.** `<state dir>/osstrich/<date>-<slug>-attempt-<N>/` holds each phase's output the moment it finishes (inventory, rank, overlap, verdict, gate, per-target build notes) and a one-line `run-record.jsonl` with the counts that measure the skill's KPI (candidates, funded, gate outcomes, PRs opened, review rounds, fork and hand patches retired). Plain files, no new dependency; if you keep a run ledger or similar record elsewhere, an adapter can append the record there too so a periodic audit can report it — that's an optional integration, not a prerequisite. The state dir defaults to `~/.osstrich` and is overridden by `OSSTRICH_STATE_DIR`. See `references/discover.md` → Run directory.
- **Classification is read from a file, never re-judged per run.** `references/classification.md` carries every project's class (community / company / company-adjacent), its reason, its last-verified date, and any override that's been ruled. A project missing from it gets a row this run.
- **Report compact and outcome-shaped.** A status update on an open PR is one line, not a walkthrough.
- **Parallelize the investigation.** Phase 1's three scouts (repo conventions, discussion history, maintainer-comment mining) ride ONE wave, fresh and blind — see `references/investigate.md`. Any prior `references/repos/<repo>.md` is read only after they join, to reconcile against, never as a starting point. Nothing here is generally sequential; treat serial scouting as something you'd need to justify, not the default.
- **Trust but verify — including your own past claims.** A note saying "opened as an upstream PR" is a claim, not a fact — check the actual PR list before repeating it. (This is not hypothetical: it happened. See `references/self-learning.md` → Keep the tracking claims honest.)
- **Explicit permission gates every outward action**, same as any other external-facing work: opening the PR itself, posting a comment, and pushing a branch that becomes visible on a public fork all need a stated go — see `references/pr-etiquette.md` → What needs a green light and what doesn't.
- **Scrub before anything goes public.** Every PR body, commit, commit author/committer identity, and branch name gets checked for personal information and your own internal system names before it's shown to you or pushed anywhere external — see `references/pr-etiquette.md` → Scrubbing. AI attribution is not scrubbed: the `Co-Authored-By` trailer and the generated-with footer stay unless the target repo's own stated policy says otherwise.
- **Borrow hardware rules from your own machine, never this repo's own git/CI rules.** This skill runs on your own machine, so whatever host-awareness you normally practice (what's actually installed, which environment you're on) still applies and gets checked like any other run; see `references/investigate.md` → Phase 0. But every git/CI convention this skill follows belongs to the TARGET repo, discovered fresh each time by Phase 1 — nothing here ever commits to your own repo, so your own repo's branch-protection, merge-gate, coverage-ratchet, or worktree rules never transfer. If a step here starts to read like a rule about your OWN repo's git flow, that's a sign it's leaked in from the wrong runbook.
- **Match swarm size to the size of the actual problem.** Most contributions are one small fix in one unfamiliar codebase — the Phase 1 scout wave plus a normal build-and-verify pass is enough; don't stand up a full builder/reviewer swarm for it. When a contribution genuinely is large (several files, several independent fixes in one sitting), split the work the same way you would any other large task: a conductor plans, verifies, and never skips checking a subagent's claim; execution dispatches to a cheaper model by default, reserving a stronger tier for a judgment-heavy reviewer.
- **The builder is an internal subagent, verified by the conductor. Not an external autonomous coding agent.** Considered and rejected: SWE-agent, OpenHands, and similar benchmark-driven patch generators are scored on making tests pass, not on the actual value this skill provides — matching a maintainer's real conventions, catching a hazard only live testing reveals, writing brief and well-mannered, knowing when NOT to build because it's already fixed. None of that transfers to an external tool, and its output would still need every check in Phase 4/5 redone before it could ship — a rewrite pass bolted onto the verification you already do, not a replacement for it. The internal subagent model also keeps everything Phase 1/2 already discovered in the same context; handing the build to a separate tool means re-explaining all of it.

## Phase index

**Stage `discover`** — `references/discover.md`
- **D1 · Inventory** — every open-source project this repo runs, from every source: lock files per tree, vendored binary pins, CI actions, container images, host installs, vendored skills, hand patches. Yours and latest per row.
- **D2 · Rank** — two ascending ranks (stars, weekly downloads), combined by average; no download figure means the star rank stands alone. Company and company-adjacent projects (`references/classification.md`) move behind every community project; overrides that have been ruled stay eligible. The bottom N, a stated count, is where effort goes.
- **D3 · Overlap** — your next steps (explicit backlog if one exists; inferred from the repo always) against their open issues and PRs, plus cases you found that they have not been told. Bottom N read in full; past N the search inverts, your side first.
- **D4 · Verdict** — one table: fixes for you, gives back, cost, who, and the four evidence boxes (reproduction, patch, production run, measurement); fund on overlap plus at least one box; defer / skip; give-back-only offered when nothing funds; your own in-flight PRs checked first. Then the gate, with its source-level method.

**Stage `build`** — `references/investigate.md`
- **Phase 0 · Frame the target** — which repo, which symptom, is this retiring one of your own fork patches (check `references/repos/*.md` and your own notes for an existing fork-provenance note first). A target arriving from `discover` brings its verdict row and gate answer.
- **Phase 1 · Parallel scout wave, then reconcile** — three scouts fire together, fresh and blind, no anchoring on old notes (one verifying scout instead when a repo note less than 30 days old exists — see `references/investigate.md`): repo-conventions (CONTRIBUTING/AGENTS.md/PR template/CI workflow/lint config), discussion (existing issues/PRs for the same symptom, prior attempts, maintainer's stated opinions), maintainer-pattern (mine recent merged/closed PRs and the maintainer's own review comments when there's no written contribution guide). **Etiquette checkpoint 1: this is where their norms are learned.** Only after they join does `references/repos/<repo>.md` (if it exists) get read at all — reconciled against the fresh findings, live facts winning any disagreement, never the other way around.
- **Phase 2 · Root-cause, verified live** — the failing test is the reproduction: written first, run against unpatched upstream, then the fix. Four outcomes: still reproduces (build); fixed upstream and you fork (retire the patch); fixed upstream, no fork (stop); avoidable by using the library differently (back to the gate).

— `references/build-and-test.md`, then `references/pr-etiquette.md`
- **Phase 3 · Build the fix** — smallest diff that fixes the root cause; match the existing file's own comment density and code shape over an abstract "best practice"; new files only when the repo's own convention already uses them for this kind of thing.
- **Phase 4 · Test hygiene** — tests land in whatever existing file already covers this area unless the project's own convention clearly separates concerns; run the *actual* local test suite and, where one exists, the project's own most-specific CI job (not just the fastest lane) before calling anything green; assert the real consuming code path, not a proxy value.
- **Phase 5 · Write and post the PR** — **etiquette checkpoint 2 (writing):** brevity, structure over prose, symptom before root cause, their commit style and changelog rule, explicit relation to any competing/sibling PRs or issues, a genuine (not decorative) note of thanks only when one is earned, full scrub for personal/internal-system info, correct author identity; then the green light, then open. **Etiquette checkpoint 3 (after opening, until merge):** a bot review is fixed then confirmed, a maintainer's question answered in their shape, a competing PR that wins gets a graceful defer.

**Stage `capture`** — `references/self-learning.md`
- **Phase 6 · Capture = one learning-pass dispatch** — hand your learning pass (if you keep one — this step is an optional adapter, never a prerequisite) the run record; it routes repo-note updates (`references/repos/<repo>.md`), any rule change, backlog items, and follow-up notes, and re-checks every "retire once X ships" note the run touched. Without a learning pass, do this step by hand: update the repo note yourself and note anything worth remembering next time. Repo-note edits and rule changes ride a small PR against your own repo, since the contribution's own PR lives elsewhere.

## Repo notes — callable per repo

This skill ships with no pre-filled repo notes — `references/repos/<repo>.md` files are created locally the first time you touch each repo, and Phase 6 adds to them as contributions land. A repo not yet in this directory has no notes — Phase 1's scouts build them from scratch. A note can also record a candidate that resolved on your side (the gate said yes) so the next `discover` does not re-fund it.

## Don'ts

- Don't rank by stars alone or downloads alone, and don't read "N versions behind" as a finding — a finding names an incident class, a dropped runtime floor, or a hand patch that would stop being re-applied.
- Don't fund a candidate with no overlap while an overlapping one exists; give-back-only items are offered only when nothing overlaps.
- Don't enter the build arc without the gate — a library that already has a hardened door you are not using turns the upstream PR into optional give-back.
- Don't invent a CONTRIBUTING.md's worth of rules from vibes — either the repo states its norms, or you infer them from what the maintainer has actually asked for and rejected on other real PRs. Never from a different, unrelated project's conventions.
- Don't open a PR, push a branch to a fork, or post a comment without a stated green-light — same bar as any other public, outward-facing action.
- Don't let a "thank you" be a value description wearing a thank-you's clothes. If it doesn't contain the words "thank you" (or an unambiguous equivalent) and a specific reason, it isn't one — say the thing and stop.
- Don't trust a diffstat's shape to tell you whether a file is new. Check the base ref directly.
- Don't let a commit meant for an external identity inherit this machine's own global git config. Verify the actual author/committer email after every commit and amend, not just after the first one.
- Don't carry a stale "opened upstream" / "tracked for merge" claim forward without checking the real PR list first — repo notes are cache, not truth.
- Don't propose a design that skips the smaller fix at the source when one is available, even if the larger diff already works — a maintainer used to reviewing this repo will ask for it anyway.
- Don't leave any of your own internal system names, local file paths, personal email, or machine hostnames in anything destined for an external repo — scrub before showing a draft, not after.
- Don't delegate the build step to SWE-agent, OpenHands, or any other external autonomous coding agent — decided against; see Operating rules above.
