# Build and test — Phases 3–4

## Phase 3 · Build the fix

- **Base everything on the target repo's real, freshly-fetched default branch — never your own pinned commit, and never a stale local clone.** If your repo vendors a fork of the target repo, that fork's own `main` and its pinned commit are BOTH allowed to lag the real upstream — a production pin optimizes for stability, not currency, and a fork's `main` only updates when someone remembers to sync it. Add the actual upstream repo as a remote (or clone it directly) and fetch its default branch fresh, every time — don't assume a clone left over from an earlier session, or the fork's own `main`, is still current. Check how far behind it actually is (`git log <starting-commit>..upstream/main --oneline`) before building anything; if it's behind at all, rebase onto upstream's current default branch first. This is not a hypothetical: a real fix branch turned out to be 19 commits behind once, caught only by fetching and diffing against the real thing rather than trusting what was already checked out.
- **Smallest diff that fixes the root cause.** Not the smallest diff that plausibly helps — the one that removes the actual mechanism found in Phase 2. A maintainer who reviews carefully will ask why a larger diff didn't stop at the source.
- **Match the file's own style, not an abstract standard.** If the surrounding code already carries dense, multi-paragraph rationale docstrings, a terse one-liner reads as inconsistent, not "cleaner" — and the reverse is just as true. Read the file you're editing before writing a single comment in it, and match its existing density.
- **Keyword-only, opt-in, default-preserving parameters over new call shapes.** When a fix needs new configurability, add it as an optional parameter whose default reproduces the exact prior behavior — verified by a test that asserts the no-op, not just claimed in a comment. This is what makes a fix reviewable in isolation instead of as a behavior change bundled with a feature.
- **New files only when the project's own convention already uses them for this.** Check whether the kind of test/module you're about to add already has an established home before creating a new one — see Phase 4 below; the same logic applies to non-test files.
- **Add a changelog entry only if Phase 1's repo-conventions scout found that contributors are expected to.** Some projects want it in the PR; others have the maintainer add it on merge and consider a contributor-added entry noise. Follow whatever the scout found, not a default habit either way.
- **Reuse the clone Phase 1 already made — don't re-clone.** Phase 1's scouts already fetched the real upstream repo fresh to investigate it; that same clone, fetched again if any real time passed, is what Phase 3 builds on. A second, separate clone risks the two silently drifting from each other mid-run and wastes the fetch Phase 1 already paid for.
- **Check the draft against any bot reviewer's checklist too, before it's ever posted — not just the human maintainer's.** Phase 1's maintainer-pattern scout builds this the same way it builds the human one, if a review bot is active on the repo. A diff that already satisfies what the bot always flags is a PR the bot has nothing left to say about; finding that out from an actual bot comment after posting is the reactive version of the same check done too late.

## Phase 4 · Test hygiene

- **Tests go in whatever file already covers this area.** Before creating a new test file, check the base branch directly for one that already exists (`git ls-tree <base-ref> -- path/to/suspected/file.py`, where `<base-ref>` is the freshly-fetched upstream default branch from the Phase 3 bullet above — not the fork's own `main`) — a diffstat showing only additions does NOT tell you whether a file is new; it tells you nothing was deleted. Confirmed once, mistaken once: this exact check corrected an initial wrong claim that a test file was newly introduced, when it had existed upstream all along and the diff only added a class to it.
- **Run the actual local suite, not a subset you assume covers it.** If the project uses a lockfile-driven installer (`uv sync --locked`, `npm ci`, etc.), use it — installing loosely can pull dependency versions CI never sees.
- **Run the project's own most-specific relevant CI job locally, not just the fastest one.** A project with a platform-specific job (a macOS-only keychain suite, a Windows-only path-handling suite) is telling you exactly which real conditions it doesn't trust a mock to stand in for. Reproduce that job's own command, on that job's own platform, if you have access to it — a real prior contribution ran the actual platform-specific contract tests on real hardware, not just the mocked cross-platform suite, and that distinction is what let the PR credibly claim the alternative approach's failure mode instead of merely asserting it.
- **A test must exercise the real consuming path, not a proxy value.** A test that checks an intermediate return value without confirming what the actual caller does with it can pass while the real bug survives — this is the single most common test-gap class a careful maintainer's own review comments will call out.
- **State exactly what ran and what passed, with real counts.** "Tests pass" is not a claim; "2,195 passed, 0 failed, plus the project's own 63-test real-hardware suite, run locally" is one. Never round up a skip count into a pass count.
- **A red check isn't necessarily yours.** Before treating any test failure as caused by the change, run the identical suite against a clean checkout of the same base branch with the change stashed out. If it fails there too, it's pre-existing — say exactly that, name the failing test, and don't spend effort fixing something outside this contribution's scope. A real prior PR did exactly this and stated the pre-existing failures plainly rather than either ignoring them or trying to fix unrelated tests to get a clean run.
