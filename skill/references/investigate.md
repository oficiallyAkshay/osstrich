# Investigate — Phases 0–2

## Phase 0 · Frame the target

A target arriving from `discover` (`references/discover.md`) already carries its verdict row and its gate answer; a target named directly (`osstrich build <repo | issue | patch>`) passes through that gate here first. Then answer four questions in one or two sentences each:

1. **Which repo, which symptom.** Name the exact upstream repo (not your fork of it, if one exists) and the observable failure — what breaks, for whom, under what condition. "OAuth session expired" is a symptom; "the ACL resets on every write" is already root cause — Phase 0 only needs the symptom.
2. **Is this retiring a fork patch?** Check your own notes and this skill's `references/repos/<repo>.md` for an existing fork-provenance note. If you're already vendoring a patch for this exact bug, this contribution's success condition includes tracking toward deleting that patch — say so in the plan.
3. **Has anyone touched this before, on either side?** Note only whether `references/repos/<repo>.md` exists — Phase 1 is where it actually gets read and used.
4. **What can actually be verified live on this machine?** This is about the TARGET repo's own tooling, not yours: is its language runtime, package manager, and CI-equivalent command actually runnable here? If the target repo's most-specific verification needs a platform this machine isn't, say so plainly in the plan rather than settling for a weaker mocked equivalent without naming the gap.

## Phase 1 · Parallel scout wave, then reconcile against prior notes

**One verifying scout when the repo note is fresh.** If `references/repos/<repo>.md` exists and its newest last-verified date is under 30 days old, dispatch one scout whose brief is the note itself: confirm or refute each claim against the live repo (the written guide, the CI shape, the maintainer's last ten merged and closed PRs, any competing PR for this symptom) and report only deltas. Three scouts rediscovering a repo you visited last week is the swarm-size mismatch this skill warns against elsewhere. Anything older, or a first visit, gets the full wave below.

**Scout fresh and blind first — no anchoring.** Three scouts, dispatched together, not in sequence — there is no dependency between them, and none of them reads `references/repos/<repo>.md` before or during this fan-out. The point is independent, live rediscovery: an old note is a claim about the past, and starting from it risks confirming a stale belief instead of finding what's actually true right now. This is not a hypothetical risk — see `references/self-learning.md` → Keep the tracking claims honest for the exact time an old note's claim turned out to be false and would have quietly passed through unchallenged if a scout had treated it as a starting point.

**Query the real upstream repo directly, never your own fork's mirror of it.** When you vendor a fork, the fork exists to carry YOUR patches and pin a stable install point — it is not a live copy of upstream and can lag it by any amount. All three scouts below hit the actual upstream org/repo (its issues, its PRs, its workflow files, its git log) directly — via its own API or a fresh clone of *it*, not the fork's `main` and not a fork's stale copy of `CONTRIBUTING.md` or CI config. Phase 3 carries the same rule forward for the actual build: base on a freshly-fetched upstream default branch, never the fork's pinned commit.

- **Repo-conventions scout.** Does `CONTRIBUTING.md`, `AGENTS.md`, a PR template, or an issue template exist? What does the CI workflow actually run (test job, lint job, type-check, multi-platform matrix)? What commit-message convention does the git log actually follow? Is there a lockfile / dependency manager whose install command CI uses, so local verification matches CI exactly? Does the project require a CLA, a DCO `Signed-off-by` trailer, or have any stated policy on AI-assisted contributions (some explicitly welcome disclosure, some explicitly forbid it, most say nothing) — check for it same as any other convention, and follow whatever it says rather than defaulting to your own habit around disclosure. Also note the changelog convention: does a merged PR here typically carry its own changelog entry from the contributor, or does the maintainer add one on merge — guessing wrong either clutters the diff with an entry nobody asked for or leaves out one that was expected. If a review bot is active on this repo (see the maintainer-pattern scout below), also check for a repo-committed config file governing its rules (bots like this sometimes ship one) — a written config, when one exists, is the more reliable source than inferring the same rules from past comments.
- **Discussion scout.** Search open and closed issues and PRs for the exact symptom, not just the suspected mechanism — someone may have already filed it, half-fixed it, or explicitly argued against fixing it a certain way. Read anything the maintainer said about the *shape* of an acceptable fix, even in an unrelated thread. A competing open PR for the same bug changes the plan (see `references/pr-etiquette.md` → Competing approaches) — find it now, not after building. Note, don't act on, a culture that expects an issue or discussion before a PR — this skill doesn't comment or participate in discussions on its own (see `references/pr-etiquette.md` → What needs a green light), so flag it in the plan as a known norm and let the maintainer of this run decide whether and how to engage, rather than silently skipping the PR or silently ignoring the norm. **Signs the project itself is inactive** — no maintainer response across the last several months of issues/PRs, no merges in a long stretch, an explicit archived/deprecated notice — are a stop condition, not a workaround-and-continue: say so in the plan and stop here. Don't go looking for a community fork or a different maintainer to route around it; that's a separate, bigger decision, not something this phase resolves on its own.
- **Maintainer-pattern scout.** When there's no written contribution guide (the common case for a smaller open-source project), the maintainer's own behavior on other real PRs *is* the contribution guide. Pull their review comments and reactions across the last handful of merged PRs and any open PRs with substantive back-and-forth. Build a short inventory: what do they routinely ask for that a contributor didn't already provide (a live reproduction, a specific edge case, a smaller diff, a real-machine test)? What's their tone when merging cleanly versus when asking for changes? What have they explicitly rejected, and why? This inventory becomes the checklist Phase 5's PR body is written against. **Tell the maintainer apart from an automated review bot.** A bot account (a distinct, often clearly-named login; a comment format that repeats the same structure every time; a command syntax like `@botname re-review`) is not the human maintainer and its verdict is not a merge decision — attribute the actual "what gets merged and why" patterns above to the human account(s) that write differently each time and whose comment is the one that actually closes or merges something. **But mine the bot's own history exactly like the maintainer's — a checklist to build against from Phase 3 onward, not just feedback to react to after posting.** If it's reviewed recent PRs on this repo, pull its past comments the same way and build the same kind of short inventory: what does it flag every time (a pattern, a missing test class, a security check, a style rule)? That checklist feeds Phase 3's build directly, same as the human-maintainer one feeds Phase 5's PR body — the goal is a PR the bot has nothing left to say about, not one that gets fixed reactively after it says something.

**Join, then reconcile against `references/repos/<repo>.md` — read last, never first.** Once all three scouts are back, read the notes file if one exists (nothing to reconcile if this is the first visit; the three fresh findings above simply stand). Compare the notes file's record against what was just independently found:

- Where they agree, the fresh finding is now confirmed, not just asserted.
- Where they disagree, the fresh, live finding wins — state the disagreement plainly (a maintainer added a `CONTRIBUTING.md` since last visit; a claimed-open PR is actually already merged or was never actually opened) rather than quietly picking one. A stale claim caught here is itself worth carrying into Phase 6's capture step as a correction, not just a silent overwrite.
- The reconciled result — not the old notes file, not the unreconciled fresh findings alone — is what Phase 2 works from.

## Phase 2 · Root cause, verified live

**First question, before anything else: does the bug still exist in the version just fetched in Phase 1?** The symptom that sent you here might describe your own vendored fork, a version pinned months ago, or a stale local checkout — none of which is the thing a PR would actually change. Reproduce against the freshly-fetched upstream default branch specifically, not against whatever was already checked out. Three outcomes, each with a different next step:

- **Still reproduces on latest upstream** — proceed below; this is a real, current contribution.
- **Already fixed upstream, and you vendor a fork patch for it** — there's nothing to build. The job becomes confirming the fix (cite the commit/PR that did it), then retiring your own fork patch per its tracked retire condition (`references/repos/<repo>.md` → Fork provenance) — a real outcome, not a failed investigation.
- **Already fixed upstream, and you don't vendor anything for it** — say so and stop; there's no contribution left to make. Update the notes file so the next visit doesn't re-discover the same dead end.
- **Avoidable by using the library differently** — live reproduction shows a supported option, a newer version, or a different entrypoint sidesteps the defect without breaking you. Send the target back through the gate (`references/discover.md` → The gate): the deliverable becomes your own migration and the upstream item drops to give-back-only.

Only once the bug is confirmed to still exist on latest upstream does the maintainer-pattern scout's usual bar apply — "prove it happened, don't just assert why it happened":

- **The failing test is the reproduction.** Write the test the PR will carry first, in the project's own test shape, and run it against the unpatched upstream default branch. Red there is the proof; green after the fix is the second half. A reproduction that lives only in a shell session is not one the maintainer can re-run.

- Reproduce the failure against real conditions wherever that's feasible — the actual OS, the actual tool version, the actual failure mode — not a plausible-sounding theory about what a stack trace implies.
- When a competing fix already exists (open or merged), test its approach too, not just read its diff. A real prior contribution's whole differentiator was that the competing PR's approach was *tested* and found to have a real, reproducible problem the diff alone didn't reveal — reading it would not have surfaced that.
- State plainly what you verified live versus what you're inferring from source reading alone. A maintainer who reviews carefully (the pattern the scout should have already surfaced) will ask exactly this question if you don't answer it first.

Present the scoped problem, confirmation it still reproduces on latest upstream, the root cause, any competing approach found, and the retire-a-fork-patch angle (if applicable) as a short plan before writing any code — same green-light gate as any other non-trivial change.
